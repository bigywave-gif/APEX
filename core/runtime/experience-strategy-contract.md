# APEX 体验策略合同

本合同将客户需求与真实代码、页面骨架、真实前端展示转化为跨场景可执行的体验决策。它不是某一种页面风格，也不是把厂商设计语言复制到项目中；它规定每个正式效果图生成前必须明确的决策。

## 证据绑定

策略必须绑定本次范围的 `code-reference.json`、`page-skeleton.json` 与真实浏览器展示证据哈希。策略不能以猜测替代已读取代码、实际 DOM、现有 Token、组件或用户需求。

## 必填决策

1. 场景与用户：识别数据洞察、管理工作流、内容阅读、协作决策、转化入口或配置管理等场景；声明主要用户、核心任务、首屏目标与成功动作。
2. 信息架构：按用户决策优先级给出内容层级、页面骨架、渐进披露和空态/异常态，禁止只把需求逐条平铺成等宽卡片。
3. 数据表达：每张图表必须回答一个具体问题，声明指标、比较维度、时间/分布/关系语义、图表类型、筛选/钻取与洞察文字。数据密集页面优先使用结论、对比、趋势、分布、异常与行动建议的组合，而非大段解释替代数据。
4. 功能与交互：列出组件、状态、权限、键盘路径、错误恢复、加载/空态、筛选、编辑、批量操作或钻取等真实前端功能；功能必须映射到代码和 API 事实。
5. 视觉系统：声明 Token、类型层级、栅格、密度、颜色语义、组件边界、图文比例与反模式；Token 应保持工具与代码之间可交换、可追踪的语义结构。
6. 响应式、无障碍与动效：声明断点重排规则，而非缩放；声明 WCAG 目标、语义、键盘交互、可访问名称与 reduced-motion 行为；每条动效必须绑定 `functionalPlan` 中的任务、事件和不同的前后状态，并说明它提供的操作反馈、状态解释、空间定位、层级引导、进度解释或风险提示。不能建立此闭环的动效不得进入方案；产品页面不允许无限循环，`delight` 仅可作为任务完成后的短暂一次性反馈。

## 公开专业依据与采用边界

- IBM Carbon 数据可视化：以用户要回答的问题选择图表，使用清晰结构、对比、节奏、层级、筛选与可探索交互。<https://www.ibm.com/design/language/data-visualization/overview/>
- W3C WCAG 2.2：以可感知、可操作、可理解、健壮作为可访问性基线。<https://www.w3.org/TR/WCAG22/>
- W3C WAI-ARIA APG：将常见组件的语义、状态与键盘模式落实为可实现交互。<https://www.w3.org/WAI/ARIA/apg/>
- Material 自适应布局：按屏幕与任务进行布局重排，而非机械缩放。<https://developer.android.com/codelabs/adaptive-material-guidance?hl=en>
- DTCG Token Format：用于设计 Token 在工具和代码之间的交换；它是社区规范，不是 W3C 标准。<https://www.w3.org/community/reports/design-tokens/CG-FINAL-format-20251028/>
- Microsoft Fluent：借鉴可复用组件、生命周期反馈与错误恢复的体验原则，不复制品牌视觉。<https://learn.microsoft.com/en-us/agents/design-guidelines/human-centered-design>

## 反模式

- 用“高级、专业、丰富”等形容词替代场景、用户任务与可验收决策。
- 用长段文字替代数据表达、比较和行动路径。
- 不区分主次地平铺卡片或重复同一种图表。
- 未读真实 DOM/代码/组件就重构页面骨架或虚构前端功能。
- 以装饰性动效、低对比或复杂布局掩盖信息层级不足。
