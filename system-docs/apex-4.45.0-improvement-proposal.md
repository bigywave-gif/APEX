# APEX 4.45.0 综合改造方案

状态：改造进行中，尚未作为 4.45.0 发布。制定方案时本地 APEX Core 为 4.44.1；GitHub 当前代码版本以仓库 manifest 为准。本文描述目标行为，具体完成情况以代码、验证证据和发布记录为准。

发布审计分别检查测试结果和版本基线。开发期间若当前文件与基线不同，`release-baseline-current` 必须报未通过；待候选版本和内容完成验证后再生成最终基线并重跑审计。不得把版本分析命令成功执行等同于基线一致。

## 目标与原则

在现有 Router、Run Ledger、角色链、能力库和验证机制上，提高稳定性、完整性、准确性、视觉质量、设计还原度及耗时与 Token 可控性。合理化不是减少必要角色、检查或校验；通过明确分工、有效复用、按影响范围重验和避免无效重试提高效率。用户通过交互式 Demo 判断是否符合自己的审美，确认后的 Demo 是代码实施基线。

借鉴 LobeHub 的角色和工具边界、取消传播与渐进加载，Super Agent 的连续任务执行和真实工具使用，以及 Harness 的持久状态、恢复、上下文管理与结果评测。APEX 保留 Router 和 Ledger 的既有职责，不另建平行主控。

## 角色与交接

1. 产品角色先确定产品目标、用户任务、页面结构、功能流程、数据、权限和验收标准。整站改造必须基于真实网站和代码，明确现状问题、保留与改造范围、预期结果；产品方案缺失时由产品角色补充。
2. 设计师依据产品方案确定视觉与交互方向，选择样式、制作并审查可交互原型。抽象的“炫酷、好看、专业”须结合用户、场景和任务转为可观察的布局、层级、密度、色彩、组件与动效决策。
3. 前端工程师在设计阶段验证技术可行性；用户确认 Demo 并选择路线后，依据确认原型、产品方案与实施范围落地代码。
4. 产品、设计、前端联合验收：分别检查功能任务、视觉品质、代码与运行行为。Router 决定阶段、授权和 Gate，角色不能自行批准或扩大范围。

两次确认模型中，选择视觉角色前须确认交付契约、包含有效任务的产品方案均为当前 Run 内可读文件；Existing 还须具备当前变更范围。缺失或越界时不得创建视觉角色任务，先恢复产品输入，避免设计师基于空方案工作。

## 现有 Skill 的协同使用

**结论**：复用 APEX 已集成的设计技能。所有视觉设计和改造任务由设计师实际加载 `taste-skill`，引用适合当前产品和页面的视觉方向与规则；其他技能依据各自适用场景按需组合，共同服务一套设计方案。技能之间不是互斥关系，必选调用也不意味着照搬全部默认风格。设计师负责综合取舍，用户通过交互式 Demo 确认最终审美。

- **taste-skill**：每次视觉设计与改造任务必须实际加载并绑定设计师任务。设计师引用其视觉方向、审美表达、构图和反模板原则，并结合当前任务采用适用规则。若缺失或加载失败，不能记录为已使用，须保留实际失败原因并修复。后台、数据大屏等场景仍须加载，但不能将不适合的默认风格强加于页面。
- **UI/UX Pro Max**：按产品与页面需求检索并引用多场景样式、配色、字体、图表和 UX 建议。
- **Impeccable**：在适用的设计与审查任务中引用视觉层级、交互、响应式、无障碍和设计打磨能力。
- **其他已有设计 Skill**：根据当前需求引用图标、动效、设计系统等专项能力，不因为其适用场景不同而排除引用。

设计师综合适用能力形成一套统一设计，而非让每个 Skill 各自形成独立方案。建议冲突时，以用户要求、产品方案、真实项目基线和已确认设计为依据取舍并记录原因。记录各能力的版本、是否实际加载、采用的规则和不适用的原因；Skill 是设计知识，不是可运行组件或样式来源。选中的组件、字体、图标和动效仍须由前端工程师验证真实来源，并用于 Demo 和正式代码。

### 调用与场景映射

视觉设计与改造由 Router 将 `taste-skill` 作为设计师任务的必选输入：实际读取当前版本的 Skill 指令，结合产品方案和项目基线明确采用哪些视觉方向与规则，形成设计决策并传递给 Demo、前端实现和验收。仅在清单中出现、名称匹配或记录“已调用”不算完成；应保存可核验的加载来源、版本或内容哈希、设计决策及其对应产物。缺失或加载失败时记录原因并修复，未解决前不得将必选调用标为通过，也不得以其他 Skill 静默替代。

`taste-skill` 当前版本侧重营销页面、作品集与改版，自身明确不以后台、数据表格和多步骤产品界面为目标。上述场景仍执行用户要求的必选加载，但设计师只能引用经判断适用的原则；具体布局、密度、数据表达和交互由更适合的能力与产品事实共同决定，不能宣称它独立覆盖全部场景。

| 场景或需求 | 条件引用的已有能力 | 作用与边界 |
| --- | --- | --- |
| 多场景视觉方向、配色、字体和组件参考 | UI/UX Pro Max | 检索候选并结合产品任务、品牌和项目技术筛选；候选不是自动生效的样式库。 |
| 产品界面、后台、表单与设计审查 | Impeccable | 补充信息层级、交互、响应式、无障碍和状态审查；不能替代真实用户任务与运行验证。 |
| 需要沉淀设计规范并向 Demo 和代码交接 | google-design-md | 将设计师已选择的视觉方向、Token 和组件规则整理为设计契约；它不替代审美判断或组件的实际来源。 |
| 现有网站或应用改造 | redesign-existing-projects | 审查现有代码、设计和功能，基于真实现状提出改法，保护需保留的行为。 |
| 极简、工业粗野主义等明确视觉方向 | minimalist-ui、industrial-brutalist-ui | 当用户偏好和产品场景适合时提供对应视觉语言；不默认套用，不混淆为通用审美标准。 |

| 用户在 Demo 确认后选择 Stitch | stitch-design-taste 等 Stitch 适配能力 | 将已确认设计约束转成 Stitch 可用的设计规范；不得静默改变已确认 Demo。 |

### 必选调用与按需协同的执行规则

- **设计师必须真实调用 `taste-skill`**：由当前设计师任务加载技能内容，记录来源、内容哈希、角色及执行回执；将适用的视觉方向和规则写入设计决策及交接产物。技能缺失、读取失败或证据失效时，应明确失败并修复，不能仅凭名称、清单或其他技能替代而判定通过。
- **其他技能按场景引用、允许组合**：设计师根据产品目标、用户偏好、页面类型和现有网站选择适用技能，记录实际采用内容及不适用项的原因。技能提供的是设计知识和候选方案；样式库、组件、字体、图标等实际来源及工程可用性仍须核实。
- **Stitch 按用户选择进入**：用户确认 Demo 并选择 Stitch 后，可按需加载 `stitch-design-taste`；将适用规则转为 Stitch 输入，并记录技能来源、采用规则、排除理由和对应 Demo 基线。与用户要求、已确认 Demo 或项目约束冲突的规则不得强加；生成结果仍需对照 Demo 验证。未选择 Stitch 或未使用该技能时，不额外增加该步骤。
- **审美由设计师负责、用户确认**：设计师综合产品方案与技能建议形成统一设计，用户通过交互式 Demo 判断是否符合预期；实际加载和规则记录只能证明过程可追溯，不能自动证明审美质量。

以上是路由参考，不是每次任务的固定技能清单。设计师依据产品目标、页面类型、现有设计系统和用户偏好选择相关能力；涉及专业方向时可并用并综合，其他现有 Skill 也可在适用时引用。按任务分阶段加载所需内容、避免重复加载，并记录实际调用与适用性；耗时和 Token 以实测为准，不能保证必选加载零成本。

例如，同一任务可以先由 `taste-skill` 提供适用的视觉方向，再结合 UI/UX Pro Max 的候选参考与 Impeccable 的产品界面审查，必要时通过 `google-design-md` 固化最终设计契约。实际组合取决于任务；每项技能的采用内容须进入设计决策和交接，不得仅写入清单。设计师统一取舍，用户通过交互式 Demo 作最终审美确认。

当不同 Skill 的风格、组件或规则冲突时，以用户明确要求和已确认 Demo、产品功能与真实项目约束为准，设计师结合无障碍、可用性和工程可行性取舍，并记录冲突和理由；不让强风格技能覆盖无关场景。设计师负责统一视觉决策，前端工程师核验来源、依赖及可实现性，再依据确认的 Demo 复刻；产品、设计、前端在最终验收中分别核对任务、视觉和真实运行行为。

验收须覆盖：视觉任务实际加载 `taste-skill`，其适用规则进入设计决策；针对后台、营销页、整站改造等代表性场景选用适配能力；缺失和加载失败不能伪装通过；冲突处理、Demo 与正式代码的设计一致性均有可追溯证据。场景覆盖和审美效果通过实际案例与用户确认评测，不因技能数量或调用次数推断质量。

**Caveman、Ponytail、research-intake** 作为内部能力使用：Caveman 精简用户可见说明，但不省略整站方案、持久化文档与验收证据的必要内容；Ponytail 引导最小完整改动和复用，但不减少必要检查或真实验证；research-intake 判断调研范围、时效和来源，不强制每次任务联网。所有 Skill 服从用户要求、项目约定及 Router 的授权和验证规则，不新增用户确认。

## 用户流程与确认

需求与项目事实分析 → 产品方案 → 设计方案 → **确认视觉改造方案** → 自动生成交互式 Demo → 产品、设计、前端内部检查 → **确认交互式 Demo** → 用户选择是否进入 Stitch → 前端代码落地 → 整体功能、设计一致性与回归验证 → 交付。

用户对未确认方案或 Demo 提出修改时，保留已认可部分并重建受影响内容；Demo 确认后，当前 Demo 成为实施基线。选择不进入 Stitch 时，自动完成内部实施准备并开始代码落地；选择进入时，以已确认 Demo 为基线处理并校验。默认不新增独立 Stitch 内容确认或实施冻结确认；如果 Stitch 引入超出已确认 Demo 的设计变化，展示差异并由用户决定，不能静默替换。来源锁、权限、变更范围和机器 Gate 保留为内部检查。

### 视觉方案展示

- **局部改造**：简洁说明哪里有问题、怎么改及理由、样式来源。内部仍完成必要的产品、设计和工程分析。
- **整站新设计**：说明产品目标、用户和任务，页面结构、视觉方向、设计规范、组件体系、样式来源、主要交互、响应式和验收边界。
- **整站改造**：结合真实网站说明现状与问题、保留和改造方式、改造后布局及交互效果、样式来源、受影响页面和共享组件，以及不变的功能与内容。

## 视觉设计、样式能力与 Demo

设计候选应使用相同的代表性内容和任务，具有布局、层级、密度、组件或视觉语言上的实质差异，并说明适用场景和取舍。设计师在 Demo 生成后审查视觉重点、节奏、密度、组件一致性、不同状态与视口；用户通过 Demo 决定是否符合个人预期。

样式能力库按设计规范、组件与模式、视觉素材和真实实现分层；按实际支持的产品场景记录覆盖与缺口。每项候选核验场景、交互和状态、技术栈、精确版本、依赖、响应式、无障碍、源码、许可证及 Demo 和正式代码的可用性。设计师负责视觉适配，前端工程师验证工程可行性。优先比较项目已有能力，外部能力需说明价值和代价。

Demo 展示代表性内容、关键交互、必要状态、目标视口和明确来源；静态截图、占位内容或无效按钮不能代替交互式原型。用户反馈应映射为保留、调整和待复核的具体内容，按影响范围重建。

Demo 本地服务只提供当前来源清单中唯一登记且内容哈希一致的文件；未登记文件不能影响预览，已登记文件变化时不能继续按原内容提供。来源清单变化后仍需重新核对确认与下游证据；文件系统并发修改和外部网络资源不由该规则单独证明安全。

两次确认流程中的 Demo 展示页面和交互旅程须记录浏览器对页面、样式、脚本、图片和字体的加载结果；观察到同源资源失败或缺少这项观察的旧证据时不能判为通过，应重新采集。该结果只覆盖采集过的页面、执行过的旅程和观察到的资源，不能替代未访问页面、动态状态或所有网络行为的验证。

Demo 浏览器会话先打开空白页，再在同源约束与资源观察生效后加载目标页面，避免检查前的无保护加载及重复加载。实际耗时影响应以项目实测为准。

## 设计到代码与联合验收

复用 Visual Bundle、Implementation Map 和来源锁，交接确认的 Demo、产品方案、页面结构、设计规则、精确组件和素材来源、交互状态、响应式、无障碍、代码目标及验证方法。工程师不能自行替换已确认设计或改变产品行为；无法实现时提出原因和可审阅的替代方案。

通过 DOM 和结构检查、实际加载来源与版本、真实交互和数据、适用视口与状态、Demo 与正式页面对比进行验证；产品角色核对任务与功能，设计师复核真实成品。现有严格视觉一致性约束应在固定浏览器、字体、视口和数据下评测误阻断；调整标准必须基于实证并经过明确决策，不能自行放宽。

现有网站中范围内待核查的运行时图片应逐个覆盖正式采集的页面和视口；不适用项需有具体理由及对应页面的浏览器观察，每项资源至少有一次实际检查。校验结果只适用于实际采集的页面与状态，不能推断其他视口、动态状态或审美质量已通过。

由服务动态提供的同源脚本和样式表，也可在正式页面中核对对应 DOM 元素、浏览器成功加载记录及无重定向的同源复核请求；其他页面若不适用，须有具体理由并核对该页面既无对应元素也无加载记录。记录只证明所检查状态下资源可加载，不证明脚本功能或视觉质量。复核可能增加一次资源请求；浏览器不支持状态字段、重定向或无法核验时保持未验证，功能仍须通过实际交互检查。

## 稳定性：调度、恢复与取消

在现有 Job 基础上验证并补齐执行尝试身份、长任务续租、提交时的执行者与输入校验、过期执行者的提交保护，以及产物、回执和尝试的绑定。只读工作可在输入未变时复用；Run 内工件应核对输入、哈希与成功回执；项目修改应核对授权和文件状态；外部副作用应使用对方支持的幂等能力或查询结果，状态不明时停止。

`state.json` 是账本投影。新建 Run 使用账本优先策略：未曾提交且与最新账本不一致的投影保留并要求核查；已提交的旧投影可按账本恢复。历史 Run 沿用兼容恢复，但不能导入未提交的 Gate、确认锁、阶段、路线或 Run 身份变化。不能据此宣称系统可抵抗任意本地篡改；宿主和旧 Run 的实际迁移仍需验证。

升级后，已进入实施阶段的旧 Run 若原 Demo 确认回执及其绑定内容仍完整，但不满足新版附加证据要求，应保留原确认并进入受控恢复，不能自动撤销方案或重新要求用户确认；恢复后仍缺证据时记录实际回执并停止同条件重试，也不能放行后续验证。若确认内容确已改变，仍按失效处理。旧证据如何补齐并继续交付仍须按实际 Run 核验，不能凭此推断所有历史 Run 均可迁移。

对于原浏览器记录缺少资源观察或控件盘点的情况，Router 可在受控恢复后从原确认绑定的 Demo 重新采集原页面、视口和交互旅程，将补充证据和操作回执写入独立目录。原确认及截图不被替换；源码、页面与旅程一致性、资源和控件覆盖、原确认、账本及操作回执均通过后，才可恢复原有后续动作。已有失败的资源观察、改变的原确认或其他证据缺失不应借此绕过；补采失败须保留实际回执，不能无限重试。

Router 对通过状态读取流程取得的对象，在提交时核对读取版本；其他动作已提交更新时，旧动作保留冲突并失败，不能覆盖新状态。尚未绑定读取版本的初始化和其他专用提交路径按各自协议处理，不能据此宣称所有并发写入均已覆盖。

Stitch 冻结和封存应绑定操作开始时的 Run 状态；远程读取或校验期间状态变化时，拒绝提交旧结果并重新核对当前 Demo 与证据。状态和文件系统写入并非同一原子事务，异常中断后仍须检查实际工件与受控回执。

新建 Run 的专业角色领取必须提供稳定领取键，缺少时保持排队；历史 Run 按既有兼容规则处理。同一领取键的回执重放只恢复现有租约，不代表应再次派发角色。首次领取与重放返回不同的派发指令；宿主须先检查既有执行，无法确认时保持未知。租约围栏只能拒绝旧结果，不能证明宿主中的旧执行已停止或避免其继续消耗 Token。

已运行角色的领取重放仅返回原租约、执行对账指令及必要技能绑定，不重新加载或传输 taste-skill 全文，也不新增技能加载事件。首次领取仍须真实加载并保存成功回执；若重放前任务已被恢复为排队，不得绕过首次加载而领取新尝试。技能发生变化时可先对账原运行，提交设计结论前仍须核验原技能绑定与当前证据。

重放响应同时给出原必选技能加载回执的 `verified` 或 `unverified` 状态；回执尚未完成、缺失或不匹配时保持未核验，先对账原执行与回执，不能将重放本身视为加载成功或重新派发的许可。

旧账本中无租约令牌的运行任务不能验证执行者身份，不得续租或提交结果；按旧任务超时规则受控恢复并记录用量未知后，重新领取任务和签发新租约。等待超时期间不能假定旧执行者已停止，也不能提前启动重复尝试。

恢复时不以同名文件或历史归档目录存在作为失效依据。缺失产物只有在 Run 内历史归档中找到完整相对路径、账本内容哈希一致的副本，并有晚于该版本登记的受控失效事件对应归档位置和产物范围，才可归档其旧记录；已重建并与账本一致的当前版本必须保留。时间或事件证据不足时保持未验证，不能推断归档已获授权。

角色汇总清单因阶段交接、失效或修复而更新时，先核对当前账本哈希，保存原始字节和归档来源，再退休旧登记并写入新版本；核对不一致时保持阻断。历史清单不能仅保留哈希而丢失原文件。

输入修正后的恢复只可退休账本中标记为输入的旧登记，不能仅凭文件名将输出证据当成输入归档；同一引用同时有输入和输出登记时，输出的哈希冲突仍须保留并调查。运行时浏览器证据出现无法证明来源的修改时保持阻断，受控重采集按既有来源和回执规则重新登记。

视觉和角色产物移动前先记录受控失效范围与目标归档位置，移动结束再记录完成事件。可核验的修改事务在中途退出后，由独占恢复者核对已移动与未移动的工件，再按原要求重放；状态或 Gate 仍引用的产物不得提前归档。源文件与归档同时存在、两者均丢失或归属不明时保持阻断。

用户提交修改后，在改变状态和工件前持久化事务身份、原始要求、检查点、影响范围、原状态版本、哈希与执行者主机和进程；同一 Run 同时只能有一个未完成的修改事务。执行者仍可能存活、所属主机不明或无法核验时等待；中断后在修复事务前阻止下游流程。状态与修改结果原子写入账本后，即使修改日志尚未写完，也可据此幂等补齐并结束事务，不重复撤销确认。状态尚未提交且原始状态、执行者及失效计划均可核验时，受控重放原始要求；缺少重放所需记录的历史事务仍需核查。

重放在账本中独占领取，同一事务最多领取三次；恢复进程被信号中断时，仅在原进程组确认退出后允许有限重试。相同确定性错误不能通过重复授权循环执行。无法核验进程组的环境保持阻断，不推断远程执行结果。

角色提交时同时核对当前选择、任务冻结的输入身份、Run 内文件路径和内容哈希；在账本提交事务内再次检查文件，避免将已变化的输入当作当前证据。文件系统上的非受控外部并发写入不受账本锁保护，后续 Gate 仍须重新核验工件及其来源。

角色失败和完成结算必须在账本事务内确认任务所属阶段与当前授权阶段一致。专业角色的成功只能通过受控 advisory 记录和校验完成，不能由通用任务成功命令绕过；通用非角色任务仍可按原路径结算。

取消 Run 时停止待执行任务，通知可取消的运行任务，处理当前 Run 的临时资源，保留必要回执，不影响其他 Run 或正式项目服务。通过中断、超时、并发、迟到提交、回执与状态之间中断、取消和重复恢复等故障测试验证。

存在运行时服务登记时，取消清理前须核验登记可读、属于当前 Run，且登记的服务记录真实存在于当前 Run。记录缺失时，仅在登记信息、当前 Run 的启动意图和同宿主进程身份一致的情况下，可据此停止该进程；其他登记损坏、引用越界或记录缺失均须保留取消围栏和现场，不能声称服务已停止。修复登记后可重试清理；没有登记的历史运行仍不能证明不存在未登记进程。

Demo 启动应通过持久化启动意图和同 Run 启动锁处理子进程创建与登记之间的中断；真实故障注入须在子进程已创建、登记尚未完成时终止启动进程，核对恢复复用原服务及后续取消。不同宿主或无法检查进程时保持未验证，不推断远程或历史进程状态。

## 完整性与准确性

将用户要求关联到产品方案、设计与 Demo、代码目标、验证场景及证据。结果区分 passed、failed、unverified 和有原因的 not-applicable。需求、设计、代码或来源变化时，按依赖关系使受影响工件失效并重建；未受影响结果在哈希与适用性验证后复用，影响不明时扩大验证范围。

区分原始事实、机器判定、专业判断和未验证内容。机器检查不替代审美判断，角色意见也不替代真实运行证据。

Existing 代码基线采集发现可识别的字面量相对模块引用无法解析时，记录引用来源、候选和当时状态，停止将本次采集判为完整；修复来源或候选发生变化后才允许重试，相同原因不得循环重试。此检查覆盖 JavaScript / TypeScript 文件及 Vue、Svelte、HTML 内脚本中可识别的静态导入、字面量 `import()` 和 `require()`；它不是完整语法解析，也不等于验证计算出的动态路径、所有别名、构建插件或运行时依赖。`require` 也可能被局部变量遮蔽，未解析结果须结合项目事实核查。旧基线缺少该检查证据时，新确认模型不得将其当作已核验；Gate 2 前重新采集，Gate 2 后应保留旧快照并人工核查恢复，不能用已修改的源码冒充原始基线。

脚本中的注释、字符串和非脚本标记内容不会因出现导入示例而被当作真实模块引用；即使示例指向的文件存在，也不得沿其依赖扩张代码闭包。模板字符串插值中的可执行导入仍须检查。扫描版本升级后旧检查不再作为当前证据，未进入 Gate 2 的旧基线需重新采集；现有扫描仍是词法近似，不保证识别所有语言语法或运行路径。

模板插值内常见正则字面量、字符类和转义字符不会被误判为插值结束；除法表达式也继续作为代码检查。正则与除法的识别仍依赖词法上下文，复杂语法不能仅凭该检查认定完整，运行时及构建证据仍然必要。

失败证据绑定采集时实际读取的源码和逐项检查时的候选状态。若源码或候选在检查后、失败回执写入前变化，恢复判断仍能识别变化；不得用回执生成时的新状态替代当次检查的观察。此机制不为有意缺失的可选依赖自动放行，尚需专门的、可追溯的审核流程。

Router 对未解析引用返回有数量和长度上限的结构化摘要，标明来源、引用、源码状态及部分候选；摘要不代表全部扫描结果，完整的已记录内容仍以受控操作回执为准。回执达到容量上限时也可能只记录部分引用，不能据此认定其他引用均已检查或通过。

为基线前审核提供受控的 `inspect-imports` 检查产物：它绑定 Run 内范围输入、项目源码哈希与未解析候选，使用内容寻址保存并登记到账本；产物固定为未验证，不是角色审核、完整代码基线或放行许可。检查记录配置读取版本，并复核范围、源码和候选：发现变化时标记漂移；未发现变化也不代表原子快照。检查限定 10,000 个源码、10,000 项未解析引用和 4 MiB 产物，超出时明确失败，不输出部分结果冒充完整检查。产物生成后的来源与候选仍可能变化，审核消费前须重新校验。

`verify-inspection` 在新的 Router 授权下只读核验当前检查产物、账本回执、范围输入、需求调整记录、源码与候选状态；通过时也只返回 `current-unverified`，不能作为放行。旧授权不得重放检查结果，漂移、篡改或失去账本绑定时返回 `stale-or-unverified`。核验与后续操作之间仍可能发生变化，实际审核及消费时必须再次绑定并复验。

受控的 `prebaseline` 角色阶段复用代码库分析师，通过持久任务、租约和用量账本逐项记录引用判断、理由及当前源码摘录。输入只发送有界投影，每批最多 50 项且不超过 64 KiB；超限时分批执行，不得截断后当作完成。领取重放只返回上下文哈希，不重复发送或派发角色。判断包括待核查的可选/遮蔽候选、需要修复或未验证，不等于批准例外；该阶段禁止生成 Gate-ready 汇总。

分批计划基于当前受控检查生成有序批次：每项引用只出现一次，每批绑定相同检查哈希和范围，并按 UTF-8 字节限制上下文。超大单项明确失败，源码或检查失效时拒绝生成计划。Router 顺序调度各批的持久角色任务，逐批核验租约和源码、记录结果及已报告用量；失败与中断必须保留原始回执，不能把计划生成当作完成审核。

Router 与 Agent 状态查询只返回每批的检查身份、上下文哈希和数量，不重复传输完整审查上下文；对应任务首次领取时仍须取得其完整批次。账本内部保留完整绑定以供核验。该规则避免状态查询重复发送上下文，实际 Token 与耗时变化须通过真实任务测量。

批次作业、会话和角色选择对外摘要最多列出 20 项并标明遗漏数量；完整选择保留在 Run 中，可按作业 ID 查询单项。其他阶段的状态不受该上限影响。该边界控制返回内容，尚不保证账本内部读取和计算成本有同等下降。

逐批判断和覆盖校验能够拒绝缺批、重复批、跨批引用、伪造摘录及过期检查；内容覆盖校验本身仍标记受控执行未验证。Router 还须分别核对每批持久作业及账本绑定的成功回执，才能认定专业分析完成；即使完成也不能据此解除基线阻断。

Router 在能从原始失败回执唯一确定当前范围时，自动衔接检查和专业角色分析；存在运行中任务时等待并对账，排队任务的证据失效时先修复，角色失败后保留原始失败并依据输入变化决定是否可重试。分析完成后仍保留未解析依赖导致的基线阻断。无法可靠确定范围或恢复状态时保留证据，不猜测范围或重复派发；基于角色结论的例外放行仍未实现。

项目适配器推荐的置信度须与实际检测证据相称：仅有 HTML 或模板文件不能证明传统多入口运行架构；已识别但缺少专用适配器的框架使用低置信度通用候选，并核查实际运行与项目约束。真实项目的只读扫描不能替代该项目的完整交付验收。

JSX/TSX 文件本身不能证明 React：根据明确依赖区分 React、Preact 与 Solid；仅发现 JSX 语法或同时发现多种前端运行时，使用低置信度候选并核查本次范围所属实现，避免把无关示例或另一框架当作当前应用。

项目扫描还须记录子包清单中可识别的框架依赖及其位置；子包依赖与根目录不一致或清单无法读取时降低全局推荐置信度，后续按本次改动的代码范围核实归属。扫描受到上限约束时保持不完整并可扩展，不能将未扫描内容视为不存在。

Existing 代码基线须冻结目标入口及已解析的传递依赖所在目录和祖先目录中已有的包清单与 TypeScript 配置，即使子包未在根工作区声明；这些文件发生变化，或原先不存在的对应配置后来出现时，须重新核对受影响基线。该规则覆盖已解析到的依赖，不能证明未解析导入或动态依赖的配置已覆盖。

静态源码闭包解析本地模块时保留其实际文件依赖，包括带查询参数或片段的导入以及 `.mts`、`.cts` 文件；这些文件变化时不得复用旧基线。尚不能解析的导入与运行时动态依赖必须在后续证据中保持未验证，不能以这些支持范围宣称全量覆盖。

对于已解析的本地导入，记录解析顺序中先于实际来源的未选文件候选；较高优先级文件后来出现时，即使原文件未变，也须失效并重建代码基线及相关缓存。该检查依赖当前解析器的候选顺序，不证明其他构建工具的解析顺序完全一致。

## Token 与耗时控制

按 Run、阶段、Agent、执行尝试和重试记录可获取的用量，区分宿主实际值、估算值和未知值。对能够拦截的调用实施 Run 与阶段预算、并发额度预留、实际结算和重试计费，并保留必要验证和恢复预算。宿主不支持拦截或完整计量时只能提供软预算和明确提示，不宣称硬上限。

角色结果未通过内容、技能或证据校验时，若能确认当前任务、会话和有效租约，应结算该次已报告用量并结束本次尝试；重试使用新租约，旧租约和重复提交不能再次计费。用量无效时标为未知；无法归属到有效任务或宿主未上报的调用不能推断为零，需在覆盖情况中明确说明。

已登记但用量未知、且没有可保留的尝试预算的宿主调用或其他记录，不能按零用量为后续任务放行；Run 预算按全局影响阻断，阶段预算按该阶段阻断。独立宿主调用可凭原观察键、阶段、用量来源和证据进行幂等补账，重新核算后再判断准入；缺少可核实数据时保持未知，不虚构补账。该机制无法拦截未接入账本的宿主调用，也不能证明宿主总量硬上限。

未知宿主用量完成补账后，同一观察键的原始未知登记仍可安全重放；重放保留已补账的实际数值，不重复记账，也不覆盖补账证据。不同阶段或不一致的用量记录仍须拒绝，后续预算准入按补账后的数值计算。

按需加载 Skill、工具和上下文；独立只读任务可受控并行；复用输入未变且仍有效的结果；失败原因未改变时不重复尝试。不得通过跳过必要角色、检查和验证降低成本。

耗时与用量对照前，只读核对账本内当前登记工件的路径、哈希及谱系；工件变化、越界，或操作和 Agent 仍在运行时，不将样本判为可对照。工件一致仅表明已登记内容未变，不能证明必要证据齐全、任务难度相同或宿主用量已完整采集。

## 环境与测试

统一 Node 版本、实际依赖、安装与 Preflight；明确浏览器和截图等能力在分析、Demo 与交付阶段的要求、替代和阻断条件。

测试分为快速测试、完整契约测试、设计到代码的端到端测试、故障注入、视觉评测和成本评测；结果明确列出已运行与未运行范围。

3. 修复稳定性：执行身份、租约、恢复、取消与环境声明。
4. 完善设计与样式能力：评测设计师、治理能力库、提升 Demo 质量。
5. 完成前端落地闭环：设计交接、代码还原和联合验收。
6. 提升完整性和效率：需求追踪、证据失效、预算和增量复用。
7. 对照评测：比较稳定性、视觉与功能质量、耗时、Token 和人工介入。

## 验收标准

- 产品先形成方案，设计师完成设计与原型，前端工程师依据用户确认的原型落地。
- 用户确认视觉方案和交互式 Demo，随后选择是否进入 Stitch。
- 局部方案说明问题、改法和样式来源；整站改造基于真实网站说明现状、问题、改法、目标效果和影响范围。
- Demo 展示代表性内容、关键交互、状态和目标视口；正式代码符合确认的 Demo、产品方案和交互要求。
- 中断、过期、并发和取消不造成错误覆盖或不可控重复执行。
- 每项适用需求有实施和验收结果；缺失、过期或错误证据不能被当作通过。
- 将耗时、Token、重试和人工介入与改造前同类任务对照，不通过削减必要检查换取速度。

实际收益须在实施后通过真实任务与故障测试验证。

跨项目适配验收要求不同项目 ID、真实项目根目录和 Run；符号链接别名不能重复计数。Run 须属于对应项目，证据文件的真实路径须留在该 Run 内，且当前状态和已验证工件须与持久账本一致。账本缺失或投影不一致时不能判定通过，应先恢复或核查。路径不同不自动证明项目、任务和环境独立，仍需结合真实交付证据审查，也不能用合成测试替代真实任务对照。

各适配器的必需检查除实际 Gate 3 外，须在 `checkEvidence` 中按检查 ID 关联当前证据来源中的 `evidenceIds`，并提供复核理由。关联证据必须仍在当前 Run 内、哈希一致，且由成功的受控操作产生；仅列出检查名称不能通过。机器只核对关联和来源，证据是否足以证明该检查仍须专业复核。
